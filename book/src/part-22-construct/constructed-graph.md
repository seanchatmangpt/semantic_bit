# Constructed Graph

The output of a `CONSTRUCT` query is not a table of rows. It is a **Graph**.

This is a fundamental distinction. While `SELECT` returns data, `CONSTRUCT` returns a **Semantic Object**. This object carries its own internal relations and can be treated as an independent unit of meaning.

## 22.1 The Graph as a Value

In a Semantic Bit system, a graph is a value. Just as an integer is a value, a graph is an immutable collection of triples.

$$
G = \{ t_1, t_2, \dots, t_n \}
$$

The constructed graph is a **new value** derived from the source graph and the query.

---

## 22.2 Closure and Context

A constructed graph often contains "closure" or "context" that was not explicitly in the template but is required for the new relations to be meaningful.

For example, if we construct a `:AccessReceipt`, the constructed graph might include:
1. The receipt itself.
2. The badge ID it refers to.
3. The timestamp of the decision.
4. The authority that issued it.

By returning a graph, we ensure that all these related facts travel together as one unit.

---

## 22.3 Named Graphs as Targets

We often label a constructed graph with a **Named Graph IRI**. This gives the graph an identity within the larger system.

```sparql
# Construct into a named graph boundary
CONSTRUCT {
  GRAPH :Delta_001 {
    ?s ?p ?o .
  }
}
```

The name of the graph acts as a boundary. It tells the system: "These triples belong to the specific construction event `:Delta_001`."

$$
\boxed{\textbf{A named graph is a bounded set of constructed facts.}}
$$

---

## 22.4 Validation of the Constructed Graph

Before a constructed graph is admitted into the main system memory, it must be validated. Because it is a graph, we can run **SHACL Shapes** against it (see Part XX) to ensure it meets our structural laws.

We do not trust a construction just because it was generated by a query. We trust it only after it has been receipted and validated.
